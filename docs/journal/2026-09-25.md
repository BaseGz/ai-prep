## 一句话结论

`|` 不是语法糖，是 `Runnable.__or__` 运算符重载，语义是「上一个的输出成为下一个的输入」；
它**只组装不执行**，要 `.invoke()` 才跑 —— 而链能不能接下去，由**类型链**保证、不由顺序约定保证：
`dict → prompt → PromptValue → model → AIMessage → parser → str`，**每一节的输出必须是下一节能吃的输入**。

→ **「`|` 为什么能这么写」这类知识没有教材** —— 它只存在于代码和源码注释里。

怎么定位到的：**不靠视频、不靠文档，改在自己 venv 里跑代码**（零 token，一个模型都不调）——
- `print(Runnable.__or__)` → 方法真实存在；再拿一个没定义 `__or__` 的普通类做反证，直接 `TypeError`
- `(a | b).invoke(1)` → 跑出 `20`：`1` 进 `a` 出 `2`、`2` 进 `b` 出 `20`，**首尾相接肉眼可见**
- `type(prompt.invoke(...))` 与下游探针收到的类型**逐字相同**（都是 `ChatPromptValue`）
- 最后用 `inspect.isclass()` / `__abstractmethods__` **直接问 Python**「Runnable 到底是什么」

**顺带挖出一个更值钱的坑**（同一天第二次撞到，性质更隐蔽）：

| 写法 | 第一棒是谁 | 结果 |
|---|---|---|
| `model \| prompt \| parser` | model（入口**严格**） | **当场报错** `ValueError` |
| `parser \| model \| prompt` | parser → model → prompt | **不报错，跑通，吐出一坨垃圾** |

第二行是`prompt` 不挑食：它收到非字典输入时**不拒绝**，而是把整个 `AIMessage`
`str()` 化后塞进 `{q}`。**静默失败比报错危险得多** —— 三步全跑完，结果全是垃圾。
