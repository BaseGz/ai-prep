# 2026-10-06 · D16 文档加载

## 一句话结论

加载器不判断正文，它只做两件事：**决定切分单位**、**把文件信息抄进 metadata**。
同一个 `load()`，一本书给你 42 条、一个网页给你 1 条、一篇 Markdown 给你 1 条 ——
「一份文档算多大」不是我定的，是加载器定的。

## 四种格式，四种切分单位

同一句 `loader.load()`，产出条数完全不同：

| 格式 | 加载器 | 条数 | 一个 Document 是什么 |
|---|---|---|---|
| PDF（42 页） | `PyPDFLoader` | **42** | **一页** |
| HTML（单文件） | `BSHTMLLoader` | **1** | **一个文件** |
| Markdown | `TextLoader` | **1** | **整篇** |
| CSV（7 行，计划外） | `CSVLoader` | **7** | **一行** |

CSV 那行不是今天的作业，是我自己要来试的 —— 四种格式并排放，才能看出「切分单位」这件事有多硬：
`CSVLoader` 把一行变成 `列名: 值` 拼起来的一段文字，`PyPDFLoader` 把一页的纯文本原样交出，
`BSHTMLLoader` 把整个文件压成一条。**它们连"切多细"这个问题的答案都不在同一个量级。**

PDF 第 1 页只有 **24 字**（封面：「X4 用户手册 / User Manual / 用户手册」），照样是一个完整的 Document。

## metadata：16 / 2 / 1

| 格式 | 字段数 | 有哪些 |
|---|---|---|
| PDF | **16** | `producer` `creator` `creationdate` `author` `moddate` `sourcemodified` `subject` `title` `trapped` `keywords` `comments` `company` + langchain 加的 `source` `page` `page_label` `total_pages` |
| HTML | **2** | `source`、`title` |
| Markdown | **1** | 只有 `source` |

PDF 那 16 个字段里，只有 2 个是 langchain 加的（`page`、`page_label`），其余全是 PDF 文件自己带的。
HTML 的 `title` 是从 `<title>` 标签里抠出来的。Markdown **连标题都没进 metadata** —— 文件名里有，字段里没有。

这说明 metadata 不是统一的，是**每个加载器自己决定塞什么**。想按栏目过滤，就得自己往 `metadata` 里补字段
（今天的活②就是在做这件事）。

## `load()` 就是 `list(lazy_load())`

`BaseLoader` 的源码只有一行：

```python
def load(self) -> list[Document]:
    return list(self.lazy_load())
```

所以两者的差别不在「有没有读完」，在 **`list()` 什么时候把生成器耗尽**。实测各阶段耗时：

| 动作 | 耗时 |
|---|---|
| 建 loader | 0.1 ms |
| **调 `lazy_load()`** | **0.0 ms** ← 一个字节都没读 |
| 取第 1 条 | 451.9 ms ← 这里才真的打开文件、建解析器 |
| 再取 1 条 | 7.4 ms |
| `list()` 全部 42 页 | 788.0 ms |

一个反直觉的点：`lazy_load()` **不等于省内存**。只要在循环里 `append` 到列表，峰值内存和 `load()` 一样，
只是把「一次性分配」变成「慢慢分配」。真正的省内存是「读一条、处理完、丢掉」。

两个值得记的细节：

**第 13 页是 99 字，差 1 个字跨过阈值。** 目录页，四十几行标题，全部没有检索价值。
阈值这种东西，边界上永远有这种「差一个字符」的情况，不是因为阈值选错，是因为**页与页之间的有用程度本来就不是连续的**。

**`section` 不是从文件内容读出来的，是从文件路径算出来的。** 目录结构里已经有一份「这是什么栏目」的信息了，
加载器不会主动抄进 metadata（它只看文件，不看目录）。所以这活儿只能自己写 —— 写完这一遍，
就知道 D20 的 metadata 过滤能用什么了。

## 最值得记的一条：编码不是细节，是环境

同一个文件、同一行代码，我的环境跑通、我这台机器的 PyCharm 里崩：

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xae in position 1683
```

原因不在代码，在**进程用什么编码读文件**：

| 环境 | `sys.flags.utf8_mode` | `getpreferredencoding(False)` | 结果 |
|---|---|---|---|
| 工具内置 shell | 1 | `utf-8` | 通过 |
| PyCharm 运行 | 0 | `cp936`（GBK） | 崩 |

`BSHTMLLoader` 不传编码时用系统默认 —— 114 个 HTML 都是 UTF-8 存的，GBK 读到第 1683 字节的中文就炸。
修法是显式传：

```python
BSHTMLLoader(str(f), open_encoding="utf-8")
```

顺带记两个容易混的地方：

1. **参数名不统一。** `TextLoader` 叫 `encoding`，`BSHTMLLoader` 叫 `open_encoding`。
   报 `unexpected keyword argument` 时，别猜，`Ctrl+点` 跳进 `__init__` 看签名。
2. **`UnicodeDecodeError` 里那个 `position 1683` 是字节位置，不是字符位置。** 第三个中文字的中间。

结论：**凡是从文件读文本，编码永远显式写。** 默认值会随机器、IDE、Python 版本变，
代码在我机器上跑通，不代表能跑。

## 计划外的两步：CSV 和 JSON

今天的作业只有 PDF / HTML / Markdown 三种，但视频里先讲了 CSV，我没有 CSV 文件，就自己造了一份 X4 参数表；
讲到 JSON 又造了一份。多花的这一个多小时，踩到三个坑，全在计划外：

| 坑 | 现象 | 原因 |
|---|---|---|
| BOM | 第一列列名变成 `\ufeffspec_id`，取值取不到 | 写文件时带了 UTF-8 BOM，Windows 记事本/Excel 导出的 CSV 十有八九带 |
| `\uXXXX` | 正文变成 `\u4f20\u611f\u5668\u5c3a\u5bf8` | `json.dumps()` 默认 `ensure_ascii=True`，只影响**正文序列化**，metadata 从不受影响 |
| `metadata_func` 不返回 | `Expected the metadata_func to return a dict but got NoneType` | 函数没写 `return`。字典是原地改了，但 loader 只看返回值，不看副作用 |

第二条最值钱：`\u` 转义后一条记录从 26 字符变成 51 字符，**约 1.96 倍**，做 embedding 时是实打实多付的 token。
