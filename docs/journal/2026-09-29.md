## 今天的坑（详细版在 `errors/index.md`）

### 坑 1 · `run(question)` 收了参数，却没用它

```python
def run(question: str) -> str:
    messages = [SystemMessage(...), HumanMessage("尾号 8899 名下两单的物流都查一下")]
if __name__ == "__main__":
    print(run("我尾号 8899 那个耳机到哪了？"))     # ← 这句被吞了
```

**现象**：改第 144 行的问句，输出一个字都不变 —— 实际问的始终是第 108 行写死的那句。
**我以为**：传了参数就会按参数问。
**实际**：`messages` 里塞的是字面量，`question` 参数从头到尾没人读。
**怎么定位到的**：写完循环以为通了，直到要换题测试时发现「换题没反应」。
**结论**：**收了不用，比不收更危险** —— 不收会立刻报 `NameError`，收了不用是静默失效。
和 D7 的「存了没递」是同一个病：**多了一层参数，就多了一个「以为它生效了」的错觉。**

### 坑 2 · `if t is None` 缩进少一层，多个 `tool_calls` 只跑最后一个

`for tool_call in response.tool_calls:` 里的分发逻辑落在循环**外面**，等于每轮只处理最后一个调用。
**现象**：单工具题全部正常；「尾号 8899 名下两单的物流都查一下」一跑就露 —— 两条 `track_package` 只执行了一条。
**实际**：少一层缩进，后面的 `t` 是循环结束时的残留值。
**结论**：**单工具测不出多调用的 bug** —— 服务端能一次给多个 `tool_calls`，
不上「一次要调两个工具」的题，这个坑永远藏着。

### 坑 3 · 工具说得含糊，模型就用常识替你补

`track_package` 早期版本对「查无此单」和「有单未发货」回同一句话：
`未找到该订单的物流信息`。模型把它读成「还没发货」，**答对了 —— 靠猜**。
换成假订单号就没有订单表兜底了，它改成「可能订单号有误，也可能尚未发货」，列出两种可能。
**结论**：**工具说得含糊，模型就替你补 —— 补对是运气，补错是事故。**
「列两种可能」看上去很周到，实际是它**真的不知道**。

### 坑 4 · `tool.invoke()` 传什么，决定返回什么

| 传入 | 返回 |
|---|---|
| 纯参数字典 `{"order_id": "x"}` | 工具的原样返回值（这里是 `str`） |
| `tool_call` 字典（带 `name` / `id` / `args`） | `ToolMessage`，**自动带上 `tool_call_id`** |

第一版验证脚本对结果取 `.content`，直接 `AttributeError`。
→ 循环里必须传 `tool_call`：`tool_call_id` 是「这条结果对应哪次调用」的唯一凭据。

## 今天动手做的

`week2-tools-agent/day09-handwritten-agent/agent_loop.py`，从零手写，不碰 `create_agent`：

1. **两个有先后关系的工具**：`find_order(phone_tail)` → `track_package(order_id)`。
   后者的参数只能来自前者的返回值 —— 这条依赖链是「必须循环两轮」的原因。
2. **模拟数据提到模块顶部**（`MOCK_ORDERS` / `MOCK_TRACKS`），两张表共享：
   `track_package` 靠订单表区分「查无此单」和「有单未发货」。
3. **`TOOL_MAP` 注册表**代替 if/elif 分发：`{"find_order": find_order, ...}`，
   `bind_tools` 直接吃 `list(TOOL_MAP.values())` —— **工具名单只有一份**。
4. **未知工具兜底**：`t is None` 时手造一条 `ToolMessage` 回填（带原 `tool_call_id`）。
   不回填 → 模型看不到任何结果 → 下一轮重复调同一个不存在的工具 → 死循环烧 token。
5. **`MAX_ROUNDS = 8`** 兜底，超了返回「超过最大轮数，已强制停止」。

## 7 题测试清单（全部实测）

| # | 题目 | 考察点 | 结果 |
|---|---|---|---|
| 1 | 尾号 8899 那个**耳机**到哪了？ | 语义匹配 + 两轮依赖 | ✅ 匹配到「无线蓝牙耳机 Pro」，没抓成充电底座 |
| 2 | 尾号 1024 的订单发货了吗？ | 订单状态 vs 物流记录 | ✅ 模型仍调了 `track_package` 交叉验证（我预判它不会调，**错了**） |
| 3 | 订单 ORD-20261020-003 到哪了？ | 空轨迹分支（绕过 find_order 直接问） | ✅ 答「尚未发货，暂无物流信息」 |
| 4 | 尾号 6666 的订单到哪了？ | 不存在的号，测幻觉 | ✅「没有查询到尾号 6666 名下的订单」+ 让核对，没编订单 |
| 5 | 你们支持退货吗？ | 不需要工具 | ✅ 一轮结束，没瞎调工具 |
| 6 | 订单 ORD-99999999-999 到哪了？ | 假订单号 | ✅「系统中不存在订单」—— 从「列两种可能」变成明确结论 |
| 7 | 尾号 8899 名下两单的物流都查一下 | **多 `tool_calls`** | ✅ 第 1 轮 `find_order`，第 2 轮两条 `track_package` 都执行，终答两单分开列 |

**额外**：把 `MAX_ROUNDS` 压成 1 跑题 1 → 正确落到「超过最大轮数 1，已强制停止」。
轮数保护是**真的能兜住**，不是写了没验的摆设。

## 框架替你做了什么（D10 / D35 要用）

手写过一遍，才看得见 `create_agent` 包了这五件事：

| # | 事 | 手写版在哪 |
|---|---|---|
| 1 | 把函数签名 + docstring 转成 JSON schema 发给模型 | `@tool` + `bind_tools`（这层 `@tool` 帮了，`bind_tools` 之外的活还是我的）|
| 2 | 循环本身：调模型 → 有 `tool_calls` 就执行 → 回填 → 再来一轮 | `for round_no in range(1, MAX_ROUNDS+1)` |
| 3 | `ToolMessage` 与 `tool_call_id` 自动配对（含一次多个调用） | `t.invoke(tool_call)` + `messages.append(result)` |
| 4 | 参数校验失败 / 未知工具 → 转成错误 `ToolMessage` 回填，不崩 | 只做了未知工具，**参数校验交给 Pydantic** |
| 5 | 轮数上限 / 中断 / 流式 / 状态持久化 | `MAX_ROUNDS`（框架里叫 `recursion_limit`） |

> 面试版说法：**「工具调用不是模型的能力，是代码的能力。模型只负责说要调谁、参数填什么，
> 执行和回传都是我的循环在干。」**
