### 一句话

**工具的价值在契约（`name` + `description` + `args_schema`），不在函数体的真假。**
Mock 函数只是把执行体简化了，「模型决定调用 → 生成参数 → 代码执行 → `ToolMessage` 回填 →
模型总结」这条链路一个字都不用改；上真实 API 时只换函数体，对外接口不变。

### 搞透的两个概念

| # | 疑问 | 答案 |
|---|---|---|
| 1 | `response.tool_calls` 里到底是什么？ | 模型「想调用工具」的**意图列表**（`list[dict]`），每项四个键：`name`（工具名）/ `args`（按 `args_schema` 推理出的参数）/ `id`（与 `ToolMessage` 配对的调用 ID）/ `type`（固定 `tool_call`）。不需要工具时它是空列表，答案才走 `content` |
| 2 | 返回写死答案的假函数还算「工具」吗？ | 算。工具 = 契约 + 执行体，教学 Mock 只简化了执行体 |

**坑 3 · `parse_docstring=True` 写成函数参数**

`def get_weather(city, if_forecast, parse_docstring=True)` —— 不报错，但函数签名里的
**每个参数都会原样暴露给模型**：`parse_docstring` 变成了 schema 里一个要让模型填的布尔字段，
`city` 的 `description` 反而丢了。
→ 教训：**装饰器配置写进 `@tool(...)` 括号；函数签名只留模型需要填的参数。**
（两版 JSON 的实测对照见 `errors/index.md` D8 那条）
