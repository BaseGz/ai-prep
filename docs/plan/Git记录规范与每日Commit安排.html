0先记住三句话

这三句话决定了后面所有细节，看不懂细节时回来对一下

1. 仓库不是给你复习用的，是给面试官看的。你复习用的是笔记，面试官看的是证据。所以目录要按「能不能被面试官直接看懂」来分，不是按「我学没学过」来分。

2. 每天都要有 commit，时间要真实。面试官会看提交记录的日期分布——连续 35 天的痕迹，比一个塞满代码但只提交过 3 次的仓库可信得多。切忌最后一天一次补 50 条。

3. commit message 是你未来的面试稿。面试问「踩过什么坑」时，你不会记得三个月前的细节，但 git log 记得。所以每条 commit 都要写正文，写清楚「现象 / 原因 / 做法 / 结论」。

面试官读你的仓库，顺序永远是：README 顶部 → benchmarks（效果数据）→ git log --oneline（看你是否真连续做了）→ 只有感兴趣才会点进源码。所以这三样东西的优先级，高于你的代码写得漂不漂亮。

1分什么板块：学 / 证 / 用

整个仓库只分三个板块，任何文件都能归到其中之一

板块 A · learning

学 · 每天的练习目录

week1-basics/ → week4-adv/，每天一个 dayNN-主题/ 文件夹，里面放当天跑通的脚本。

作用：证明你每天在学。面试官基本不会细看，但目录整齐本身就传递「这人做事有条理」。
板块 B · evidence

证 · 能证明你动手调过的东西

experiments/（对比实验数据）、errors/（报错档案）、docs/decisions.md（技术选型）、benchmarks/（提效度量）。

作用：这是整个仓库最值钱的部分。「你怎么切的、为什么」「踩过什么坑」「怎么证明省了时间」——三张考卷全在这里。
板块 C · product

用 · 能演示的完整作品

project/，第 5 周的唯一产物。有 README、有数据、有界面、有提效表。

作用：面试 80% 的时间会花在这里。没有它，前 28 天在面试里几乎等于白学。

为什么把「证」单独拎出来，而不是把实验散在各个 day 文件夹里？

因为散着放，面试时你要翻 35 个文件夹才能找出一份对比数据，等于没有。集中在 experiments/ 下，面试前 5 分钟就能打开四个实验的结论页——切分对比、检索方案对比、RAG 评估表、提效度量表。这四份东西就是你面试时手里的牌。

两条容易忽略的规则

① 能重新生成的东西不入库，生成它的代码必须入库。向量库文件（chroma_db/）、虚拟环境、__pycache__ 全部 gitignore；但数据管线脚本一定要提交——「别人 clone 下来能重建整个库」才是工程能力。

② 大文件和密钥永不入库。数据集超过 10MB 就把原始文件 gitignore，只提交 datasets/README.md 说明来源。.env 一旦推上去，key 就永久留在历史里，删文件也救不回来。

3每次 commit 写什么

标题说清「做了什么」，正文说清「为什么这么做、结论是什么」

标题格式

<type>(<scope>): <中文一句话，用动词开头>

type 只用这 7 种

type什么时候用对应你计划里的哪一天
feat做出了一个能跑的新东西绝大多数天，如 D2 切模型、D8 工具、D19 RAG 基线
exp跑了一组对比实验，有数据D3 参数对比、D17 切分、D18 选型、D21 检索、D23 评估、D34 提效
fix修掉一个 bugD11 异常中断、D33 超时重试
refactor功能没变，代码结构变了D5 改 LCEL、D26 RAG 改图结构
docs日志、README、决策记录、面试题每天都可能有
chore环境、配置、依赖、仓库维护D1 环境、D33 干净环境验证
test测试代码可选，做 RAG 评估脚本时可用
exp 是这里唯一非标准的类型，但对你最有价值。面试官搜 git log --grep="exp" 就能一次看到你所有做过对比实验的痕迹——这比任何自述都硬。别把它混进 feat。

scope 用模块名或 day 编号

scope含义
day09当天的练习目录（week1–week4 都用这个）
rag / langgraph / assistant已经成型的模块，跨天迭代时用
chunking / retrieval / rag-evalexperiments 下的实验名
project第 5 周主项目
journal / decisions / feedbackdocs 下各类文档

正文用「四段式」——这是核心

不用写长，每段一两句就够。但这四段决定了三个月后你还讲不讲得出来。

段落写给谁看
现象发生了什么（报错、结果不对、效果差）
我以为 / 原因你当时的错误判断，以及真实原因。「我以为」这一段最值钱——面试官能从中看出你是想过的
做法最后怎么改的
结论一句话可复用的经验，面试时直接说这句

每天的 commit 数量

每天 至少 2 条（代码 + 日志），不超过 6 条。一个 commit 只做一件事——把「加了工具」和「修了工具的 bug」分成两条，别合成一条。

4同样一天，好坏两种写法

以 D9「手写 Agent 循环」为例——这是整份计划里最重要的一天

✕ 大多数人的写法
git commit -m "update"
git commit -m "学习"
git commit -m "完成第9天内容"
git commit -m "修复bug"
✓ 你应该的写法
feat(day09): 手写 while 循环 Agent，脱离框架

现象：模型返回的 tool_calls 结构看不懂，
     第一次直接把它塞回 messages 报错
原因：tool_calls 是「意图」不是「消息」，
     必须先执行工具，再把结果包成
     ToolMessage 回传
做法：循环 调模型 → 有 tool_calls 就执行
     → 追加 ToolMessage → 直到没有
结论：框架替我做的就是循环控制 + 消息
     组装 + 异常兜底；模型本身没有
     任何执行权限，权限全在我代码里

差别在哪：左边那四条，三个月后面试时你只能说出「我手写过 Agent」。右边这条，你能直接讲出「模型不执行任何东西，它只输出意图」这句话——面试官听完就知道你不是调包侠。

而且右边的细节是当天记住的，不是事后编的。事后补的笔记会变成「我学会了 Tools 和 Agent」这种废话，因为细节已经忘了。

5用 PyCharm 提交（替代命令行）

下面 35 天里所有的提交内容都按 PyCharm 的操作来；命令行只是备选，两边的文字内容完全一样

每天固定四个动作

#动作要点
1Ctrl + K 打开提交窗口注意：Ctrl + K 会默认勾选整个 changelist，也就是当天所有改动。不属于这条 commit 的文件必须手动取消勾选——这一步决定了你的提交干不干净
2勾选这条 commit 要含的文件一条 commit 只勾一个主题。「加了工具」和「修了工具的 bug」要分两次勾选、提交两次
3粘贴提交信息点下面对应那条的「复制消息」，粘进窗口下方的输入框。第一行是标题，空一行，后面是四段正文
4Commit / Commit and PushCtrl + K 提交本地，Ctrl + Shift + K 推送。一天结束时推一次就够，不用每条都推
PyCharm 的提交框是一个大文本框，没有分开的「标题」和「正文」字段。Git 是按「第一行 + 一个空行」来切标题和正文的，所以那个空行必须留，否则你整段消息会变成一条超长标题，git log --oneline 里会糊成一团。

三个必须改的设置

路径：File | Settings | Version Control | Commit（Mac 是 PyCharm | Settings），快捷键 Ctrl + Alt + S 打开设置后搜 commit 最快。

设置项建议为什么
Clear initial commit message勾上PyCharm 默认会把上一次的提交信息自动填进输入框。你的消息是四段长文，不清空就得每次全选删掉，非常烦
Force non-empty commit comments勾上防止手滑提交一条空信息的 commit
Reformat code / Rearrange code / Optimize imports全关这三个会在提交前自动改你的代码，让 diff 里混进一堆和今天无关的改动。学习阶段最忌讳这个——diff 一乱，「今天到底改了什么」就说不清了

同页面的 Commit message inspections 区域，把「限制主题行宽度」和「限制正文行宽度」都勾上、都设 72。写太长时 PyCharm 会标黄提醒，帮你自然写成多行。
（Analyze code 可以留着，它只提示、不改代码。）

最省事的一招：把四段式设成默认模板

PyCharm 支持 Git 的提交模板。把 gitmessage-template.txt 放进仓库根目录、改名为 .gitmessage，然后执行一次：

git config --local commit.template .gitmessage

之后每次打开提交框，「现象 / 我以为 / 做法 / 结论」四段骨架已经在那儿了，你只要往里填。
必须配合勾上 Clear initial commit message，否则上一条的旧消息会盖住模板。以 # 开头的行 Git 通常会自动删掉，所以模板里可以放心写提示——但第一次提交后请用 git log -1 看一眼，如果那些提示行没被删掉，就把 # 行从模板里去掉。

还有两个 PyCharm 专属提醒

  • 第一次提交时 PyCharm 会问 .idea/ 要不要纳入版本控制，个人学习仓库直接选忽略。
  • 打 tag 在 Git 工具窗里：Alt + 9 打开 → Log 标签页 → 右键某条 commit → New Tag。只在 8 个里程碑日做这一步，对应下面表格里标了 tag 的那几天。
  • 提交前点一下文件看 diff。这是 PyCharm 比命令行强的地方——你能一眼看出有没有混进无关改动，多用。

每天列出目录和几条 commit。点「复制消息」直接粘进 PyCharm 的提交框；标 重点 的四天不要跳过

7禁入清单与提交前自查

这些是新人最常犯、且后果最严重的错误

.gitignore 第 1 天就要写好

最后两行的思路要记住：向量库和原始数据不入库，生成它们的脚本入库。

永不提交的东西

东西为什么
.env / API Key推上去就永久留在历史里，git rm 也删不掉。写 .env.example 代替
向量库目录、模型权重体积大、可再生。别人 clone 后跑一遍脚本就该重建出来
超过 10MB 的数据集GitHub 单文件超 100MB 直接拒收；大文件放 raw/ 并 gitignore，用 README 写清来源
临时调试脚本、check.js 这类删掉或放进 scratch/ 并 gitignore，别污染主目录
别人的代码直接拷进来教程源码照抄一定注明出处，否则面试问细节你答不上来，反而扣分

提交前自查 4 问

  • 这条 commit 能不能用一句话说清？说不清就是做的事太多，拆成两条。
  • 代码跑过一遍了吗？提交跑不起来的代码，等于给自己的仓库埋雷。（git commit --amend 可以救，但别依赖它）
  • 今天的结论写下来了吗？没有结论的一天，等于没学——因为三天后就忘了。
  • 有没有把 key 或大文件带进去？git status 看一眼再 add，这是唯一一次能反悔的机会。

分支与 tag 策略（保持极简，别给自己加负担）

分支：日常就在 main 上一条线走，不要每天开分支。只有两种情况才开：① 第 5 周做项目的新功能，用 feat/project-xxx；② 做破坏性改造（D26 把 RAG 改成图结构）时，开一条 experiment/ 分支试，成了再合。目的只有一个：保住 D19 那个能跑的 RAG 基线不被搞坏。

tag：每个阶段的成品都打一个，共 8 个。这样面试前你能一句话说清进度，也能随时回到任意一个可用版本演示——演示翻车时，回滚到上一个 tag 只需要一条命令。

最后：README 顶部放什么

面试官只会给你 3 分钟。所以 README 最上方不要写「本仓库用于学习 LangChain」，直接放三个链接：

① 效果数据 → project/benchmarks/（100 条人工 40 分钟 vs 工具 2 分钟）
② 我踩过的坑 → errors/index.md
③ 演示视频 → 2–3 分钟链接

这三个链接点完，你已经比 90% 的候选人更能打了。剩下的源码，感兴趣的人自然会看。
