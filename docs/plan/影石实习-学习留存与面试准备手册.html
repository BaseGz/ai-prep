学习留存与面试准备手册

学的时候留下什么 · 每天要问自己什么 · 面试能拿出什么 · 面试官会问什么

先说结论：面试官不会考你「LangChain 有几个组件」，只会问「你做过什么、怎么做的、为什么这么做」。所以从学习第一天起，你产生的副产品（代码、踩坑记录、评估数据、演示录屏）才是真正决定成败的东西。这份手册就是告诉你哪些副产品必须留。

一、学习过程中必须保留的东西

按「每天 / 每周 / 项目期」三层来留，留的东西要能被陌生人看懂——这是判断标准。

每天留（10 分钟内能做完，不要偷懒）

  • 代码 commit。哪怕只有 20 行，当天推一次 GitHub。仓库要有连续的提交记录——面试官点开你的 GitHub，看的是「有没有在持续做」，不是「代码多漂亮」。
  • 一条结论式笔记（3 行以内）。不是记「今天学了 Tools」，而是记「Tools 的本质是模型输出 JSON 意图、代码负责执行，所以模型本身没有权限」。流水账没用，结论才有用。
  • 报错 + 解决方式。这是全场最值钱的东西。格式：现象 → 我以为是 A → 实际是 B → 怎么定位到的。面试问「你踩过什么坑」时，这个能直接答，而且答得具体就赢一半。

每周留

  • 一个能跑起来的产出。能跑 > 功能多。跑不起来的代码等于没写。
  • 200 字周复盘：这周搞懂了什么 / 还没搞懂什么 / 下周要验证什么。三个月后回看，这份复盘就是你面试前最好的复习材料。
  • 一张截图。界面、trace、终端输出、评估表格——都可以。面试演示时你会庆幸自己留了图。

项目期必须留（这决定面试成败）

二、学习时要一直问自己的问题

把这些问题贴在你写代码的窗口旁边。它们不是学习内容，是学习方式——直接决定你面试时能不能讲深。

每学完一个组件，问三句

  • 它解决什么问题？没有它会怎样？答不出来说明你只是会背 API。比如 LCEL——没有它你也能串流程，那它到底带来了什么？
  • 这一行是我写的，还是框架替我做的？这是区分「调包侠」和「工程师」的分界线。Agent 的循环、消息的拼接、历史的裁剪，哪些是框架做的？
  • 如果让我写个简化版，我会怎么写？不用真写，但要能说出思路。手写过一次 Agent 循环，你对框架的理解会完全不一样。

每做一个技术选择，问三句

  • 我为什么选 A 而不是 B？选 Chroma 是因为本地零配置，不是因为它最好。
  • 代价是什么？每个选择都有代价。说不出代价，说明你还没理解这个选择。
  • 什么条件下我会换掉它？数据量到多少换 Milvus、成本到多少换成小模型——能回答这个，你在面试官眼里就是「有判断力的人」而不是「跟着教程走的人」。

每周问自己

  • 这周做的东西，能给别人用吗？不能的话，下周想办法让它能用。JD 有一条是「有把工具交付给别人真正用起来的经验」。
  • 我能不能用 3 分钟给外行讲明白它？讲不明白，就还没真懂。
  • 这周有什么是我「以为懂了但其实没懂」的？把它找出来，下周第一件事就是验证它。

每做一个功能，问一句

  • 谁会用这个功能？能省他多少时间？我怎么证明？这是 JD 最后一条原文「做工具时会想怎么证明它省了多少时间」。从现在起每做一个功能都问一遍，面试时你就有源源不断的例子。

三、面试时可以拿出什么（按优先级）

顺序东西怎么用
1 核心可演示的 AI 项目面试时主动说「我做了个东西，可以直接看」，然后 2 分钟跑完主流程
2 核心提效数据表演示完立刻给数据：「100 张图人工 40 分钟，工具 2 分钟」
3 加分GitHub 仓库 + README简历上放链接，面试前对方会点开看
4 加分2 分钟录屏网络或环境出问题时的兜底，也能发在简历附件里
5 加分踩坑记录 / 实验对比被问「遇到最难的问题是什么」时直接调出来讲
6 可选技术笔记 / 博客把踩坑记录整理成文发出去，能反向带来机会
一句话原则：能演示 > 能看代码 > 能讲原理。不要花时间把 GitHub 装修得很漂亮，要把 Demo 调到能稳定跑通。前者是自我感动，后者是面试通过率。

四、面试官大概率会问什么

点开每条看回答要点。答案里加粗的都是「答到点上」的关键句——面试官在等的其实就是那一句。

A · 开场与项目
讲一下你最近做的这个 AI 项目
用固定结构讲，25 秒到 40 秒：问题 → 方案取舍 → 结果数据 → 踩过的坑。 不要从技术栈开始讲，要从「我遇到了什么问题」开始。例如：我们有一批素材要人工打标签，一个人一天只能处理 200 张，我做了个工具把这步自动化到 2 分钟。 关键是把「去掉这个 AI，事情还能不能做」讲清楚——能讲清楚，说明你做的不是玩具。
这个项目里哪部分是你自己写的？
这是过滤「AI 生成的简历项目」的问题。答法：分三层说清楚。
  • 业务流程和数据结构是我设计的（哪些字段、怎么流转）
  • 模型这部分我用了框架的 X，但工具函数和检索逻辑是我写的
  • 模型给的代码我会先看它的调用链，跑不通就自己改
提前准备一个「我改过 AI 生成的错误代码」的具体例子，这个例子能一次回答好几个问题。
B · LangChain 与框架理解
为什么要用 LangChain？直接调 API 不行吗？
不要答「因为方便」，要答出它的边界。
  • 它解决的是三件事：多模型接入标准化（换供应商只改一行）、组件可替换（向量库/Embedding 随时换）、以及 Agent 循环这种容易写错的逻辑有成熟实现
  • 但简单场景我不用它。只调一次模型、要个摘要，直接调 API 更轻，还少一层依赖
能说出「什么时候不用」，比说它多好更能证明你想过。
Tool Calling 的原理是什么？
关键句：模型不执行任何东西，它只输出「我想调哪个函数、参数是什么」的结构化请求，真正的执行和结果回填是我的代码做的。 所以：
  • 工具函数必须由我实现，模型只负责决定调不调、怎么传参
  • 调用结果要以特定角色（工具消息）塞回对话里，模型才能基于结果继续推理
  • 模型看的是函数名和参数描述——描述写得烂，模型就选错工具，所以文档字符串很重要
Agent 会不会死循环？怎么防止？
会。要有兜底：
  • 设最大迭代次数上限，超了就直接返回当前结果并报错
  • 给工具加超时，避免外部接口卡死整个循环
  • 工具执行失败时，把错误信息作为结果回传给模型，它通常会换个方式重试——不要把异常直接抛出去中断整个循环
  • 在提示词里明确「如果连续两次拿不到有效结果，就告诉我失败原因」
LangChain 和 LangGraph 有什么区别？
LangChain 是组件层（模型、提示词、工具、检索的标准化接口），LangGraph 是编排层（状态、节点、边）。 一句话对比：LangChain 帮你把「单步操作」写整齐，LangGraph 帮你把「多步流程」画成图，尤其是需要条件分支、循环、人工介入、断点续跑的场景。 「Agent 其实就是一个 while 循环」——LangGraph 把这个循环显式地画出来，所以更可控、可调试。
C · RAG（几乎必问）
你的文档怎么切分的？为什么这么切？
答不上来的话，这一题基本就凉了。要有实验支撑：
  • 我试过 500 / 1000 / 2000 三种粒度，500 太碎会丢上下文，2000 检索精度下降，最后选 1000 加 15% 重叠
  • 切分要跟着文档结构走：按标题层级切比硬按字数切效果好，因为一个完整的语义单元更容易被检索对
  • 还留了原文位置信息（metadata），方便回答里给引用来源
有数字、有取舍、有对比——这三样凑齐，这题就是加分题。
检索结果不准确，你怎么排查？
这是一道流程题，展示你会不会系统排查，比给一个答案更重要：
  • 先看是检索的问题还是生成的问题——把检索到的片段单独打出来看，命中了没有
  • 如果是检索问题：切分粒度不合适？Embedding 对中文不行？查询词和文档用词不匹配（这时候上混合检索）？
  • 如果是生成问题：检索到的片段是对的但模型没用——检查提示词是否明确要求「只根据给定资料回答」
  • 加一层重排序（Rerank），把召回的候选重新打分，通常能明显改善 top 结果质量
怎么评估你的 RAG 好不好？
答「感觉回答得挺准的」= 不合格。 正确答法：
  • 建一个测试集：20–50 个问题 + 标准答案，覆盖常见问题、边界问题、问不到的问题
  • 分两段评估：检索命中率（正确答案所在的片段有没有被召回）和答案正确率（生成的回答对不对）
  • 再看成本指标：平均耗时、平均 token 消耗
  • 每次改动（换切分、加 Rerank）都跑一遍，用数字决定留不留这个改动
能说出「我怎么证明它变好了」，就已经超过大多数实习候选人了。
RAG 和微调（Fine-tuning）怎么选？
一个口诀：RAG 管「知道什么」，微调管「怎么说、怎么做」。
  • 知识是动态的、需要引用来源、要能随时更新 → RAG（改文档即可，不用重训）
  • 要固定输出风格、语气、格式，或者特定领域的表达习惯 → 微调
  • 成本上：RAG 便宜得多，微调要数据、要算力、要迭代周期
  • 实际项目里常见的是先 RAG，不行再考虑微调，而不是二选一
模型产生幻觉怎么办？
分三层防：
  • 输入侧：检索质量先做好，垃圾进垃圾出；提示词里明确「只依据给定材料回答」
  • 输出侧：强制返回结构化结果，包含「答案 + 依据片段 + 是否找到依据」；如果没检索到就让它说「资料里没有」，而不是硬编
  • 兜底：界面上展示引用来源，用户能自己核对——把可验证性交给用户，这是内部工具很重要的设计思路
D · AI 提效（JD 明确要求，一定会问）
你平时怎么用 Cursor / Claude Code 这类工具？
不要答「帮我写代码很方便」，要答出你的工作流。准备一个具体流程：
  • 先自己拆需求和定接口，再让 AI 填充实现——不让 AI 决定结构
  • 写测试或样例数据先给 AI 当上下文，它给的代码正确率明显更高
  • 报错时把完整堆栈和相关文件一起给它，而不是只贴一行错误
  • AI 给的代码我一定跑一遍再信——它写得像对的，不代表是对的
最后补一句它的边界：复杂业务逻辑和跨文件重构我还是自己来，AI 在那些地方容易「看起来很合理但是错的」。
有了 AI 工具，你觉得你的核心竞争力是什么？
判断力和验证能力。 AI 能写代码，但决定「写什么、为什么这么写、写完了怎么证明是对的」还是人。 具体说三件 AI 目前做不好的事：把模糊需求变成可执行的方案、在多个方案之间做取舍并承担后果、以及验证结果是否真的解决了问题。
你做的工具，怎么证明它省了时间？
这是 JD 里最独特的一条，一定要准备一个真实数字。 模板：
  • 基准：找真实场景，人工做 100 个样本，计时（比如 40 分钟）
  • 工具：同样 100 个样本，计时（比如 2 分钟）
  • 质量：不能只看快，还要看准确率（人工 95% vs 工具 90%，差值可接受）
  • 结论：单次省 38 分钟，按每周用 5 次算，一周省 3 小时
顺便说明样本量和统计方式——这会让面试官觉得你是认真测过而不是拍脑袋。
E · 工程基础与协作
接口调用失败、超时怎么处理？
  • 超时：所有外部调用都要设超时，不能默认无限等
  • 重试：只对可恢复的错误重试（限流、网络抖动），并且要指数退避，不要立即重试打爆对方
  • 降级：模型不可用时给明确提示，而不是页面卡死
  • 日志：把请求参数、耗时、结果状态记下来，出问题能定位
你了解 MCP 吗？
一句话定义 + 一个对比。 MCP 是一套标准化协议，让模型能统一地访问外部工具和数据源。它和「我自己写工具函数」的区别在于：自己写的工具只服务于自己这个应用，MCP 让同一个服务能被不同的 AI 客户端复用——写一次，Claude Code、Cursor 都能连。 如果做过小 Demo，直接说「我写过一个 server，让 Claude Code 连上了我本地的 X」，比背定义强十倍。
你怎么保证多轮对话的记忆不会爆掉上下文？
  • 只保留最近 N 轮 + 一份滚动摘要，而不是全量历史
  • 把长期信息（用户偏好、关键结论）抽出来单独存，需要时再注入，而不是塞在对话里
  • 结构化数据比自然语言省 token——能存字段就不存一句话
  • 用框架提供的消息裁剪/摘要机制，但要知道它什么时候裁、裁掉了什么
F · 岗位匹配与软素质
为什么想来影石？为什么做内部工具方向？
要具体，不要说「贵司是行业龙头」。 可以聊：影石是做影像产品的，而 AI 在影像素材的处理、检索、整理上有天然空间；再加上 JD 里提到的设计工程、内部工具方向，正好是你想做的——不追求做最炫的模型，而是想做真正被人每天用起来的东西。 有作品能对应这个方向，说服力会强很多。
你还在上学，能保证每周 5 天、连续 6 个月吗？
这是硬性条件，JD 写明了，一定会确认。提前想清楚并诚实回答：
  • 说清你的课程安排和可行的到岗时间，给出具体日期
  • 如果确实有冲突，明确说明能保证的天数，不要含糊承诺
  • 补一句你是怎么安排时间的（比如已经提前修完某门课）——体现你是规划过的，不是随口答应
你还有什么想问我们的？
一定要问，而且要问能体现你在想「怎么把事做成」的问题：
  • 团队现在做的内部工具，主要服务哪些角色？
  • 一个新工具从想法到被人用起来，中间大概走什么流程？
  • 实习生做的工具，通常怎么衡量有没有效果？
避免一上来就问薪资和转正。

五、学习过程中要特别注意的

  • 别只留代码，不留「为什么」。三个月后你会忘记当时的选择理由，而面试官最想听的就是理由。写下来的成本是 3 行字，不写的代价是面试时讲不出深度。
  • 别等到最后再整理作品集。项目做完了再回头补 README、补数据，细节全忘了。每做完一个阶段就顺手写一段。
  • 别做「只有自己能跑」的项目。换个环境就报错的 Demo，演示当天就是灾难。项目期最后一件事一定是在干净环境里重装跑一遍。
  • 别把「学完了」当成目标。面试官不看你学了什么，只看你做出了什么。每学一个模块，都要有一个能拿出来的小产出。
  • 别忽略「非技术」的留存。你怎么用 AI 提效、怎么和需求方确认、怎么决定优先级——这些 JD 明确在问，但没人会主动记录。从现在开始记。
  • 给每个阶段留一张「证据」。截图、trace、对比表格。面试是信息不对称的博弈，证据越多，你的话越可信。
