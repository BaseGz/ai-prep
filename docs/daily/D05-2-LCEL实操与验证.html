"""D5 补课 · 管道符到底做了什么（零 token，一个模型都不调）

★ 看不懂 Runnable、也不知道什么叫「重载」？先跑同目录的 learn_runnable.py。
  那个脚本从「普通函数」和「你自己写的 + 号」讲起，五步走到这里，一个 LangChain
  概念都不预设。跑完再回来看这个文件，就都认识了。

跑完要能不看笔记说出：
    | 是 Runnable 重载的 __or__，拼出来的是 RunnableSequence，
    语义就是「上一个 Runnable 的输出，成为下一个 Runnable 的输入」。
"""
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import Runnable, RunnableLambda, RunnablePassthrough

print("=== 1) `|` 是谁定义的 ===")
print("Runnable.__or__ =", Runnable.__or__)

print()
print("=== 2) 两个假组件：看数据怎么流 ===")
a = RunnableLambda(lambda x: x * 2)     # 1 -> 2
b = RunnableLambda(lambda x: x * 10)    # 2 -> 20
chain = a | b
print("type(a | b)       =", type(chain).__name__)
print("(a | b).invoke(1) =", chain.invoke(1))

print()
print("=== 3) prompt 吐出来的到底是什么 ===")
prompt = ChatPromptTemplate.from_messages([
    ("system", "说话极简"),
    ("user", "{q}"),
])
pv = prompt.invoke({"q": "你好"})
print("类型 =", type(pv).__name__)
print("内容 =", pv.messages)

print()
print("=== 4) 下游收到的就是上游吐出的那个对象 ===")
seen = {}


def probe(x):
    seen["t"] = type(x).__name__
    return "收到"


(prompt | RunnableLambda(probe)).invoke({"q": "你好"})
print("下游收到的类型 =", seen["t"], "   <- 和第 3 步同一个类")

print()
print("=== 5) 链的入口决定 invoke 要传什么 ===")
seq = prompt | RunnableLambda(probe)
print("第一个环节 =", seq.first.__class__.__name__)
print("所以 invoke 传的是 {'q': '...'}，不是字符串")

print()
print("=== 6) 左边不是 Runnable 也能接管道（__ror__）===")
factors = {
    "a": RunnableLambda(lambda x: x + 1),   # 1 -> 2
    "b": RunnablePassthrough(),             # 1 -> 1（原样透传）
}
combo = factors | RunnableLambda(lambda v: v)
print("type(dict | Runnable) =", type(combo).__name__)
print("(dict | Runnable).invoke(1) =", combo.invoke(1))

# 注意：这里要用一个只吃 a / b 的模板。
# 不能复用第 3 步那个 prompt —— 它只认 {q}，收到 {'a':...,'b':...} 会报 KeyError。
ratio = ChatPromptTemplate.from_template("{a} / {b}")
print("(dict | prompt).invoke(1)   =", (factors | ratio).invoke(1).messages[0].content)

要看的就三处，看懂了这 15 分钟就值：

  1. 第 2 步：1 进 a 出来 2，2 进 b 出来 20。 两次函数恰好首尾相接 —— 这就是「上一个的输出成为下一个的输入」的字面意思， 不用记，看一眼就懂。type(a | b) 是 RunnableSequence（不是一个新类，是把两步装进一个容器）。
  2. 第 3 步和第 4 步的类型一模一样（都是 ChatPromptValue）。 这是最直接的证据：下游收到的，就是上游吐出的那个对象本身，没有任何转换或猜测。 正因为形状对得上，管道才通。
  3. 第 6 步：左边放一个字典也能接管道。因为 Runnable 除了 __or__ 还实现了 __ror__（反向）：当左边不是 Runnable 时，Python 会去问右边「你能接住它吗」。 字典里的每个值会被当成一个 Runnable 并行跑，输入原样分给每个值 —— 所以 1 进来变成了 {'a': 2, 'b': 1}。
    为什么这条对你后面重要：RAG 的标准写法就是靠它 —— {"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | model | parser。 D15 你会亲手写这一行，今天先认识它。

源码也在你本机，想再确认一层可以打开 .venv/Lib/site-packages/langchain_core/runnables/base.py： 第 656 行是 __or__ 的 docstring（写着 compose 成 RunnableSequence）， 第 3362 行起是拼接实现 —— 就是把 self.last 和 other.first 接起来。不用读源码，知道在哪就行。

所以第 2 节做的不是「补一节课」，而是换一种学法：从「听人讲」换成「跑出来看」。 这也是以后遇到框架问题的通用办法 —— 三步：

  1. 先搜官方文档：找得到就用，找不到就别硬找；
  2. 再看类型：print(type(x))、print(type(a | b)) —— 类型会告诉你它到底是什么；
  3. 最后看源码：在 PyCharm 里把光标放在 | 那一行，按 Ctrl + B（转到声明）， 会跳到 base.py 的 __or__ —— 那句英文 docstring 就是这个知识点唯一被写下来的官方定义。
如果你还想上网找文章读，注意有一处很常见的错误。 我替你搜过了：讲这件事的中英文文章都有，多数讲对了； 但至少有一篇把「| 是 Python 3.10 引入的语法糖」当成了结论 —— 这是不准确的。

__or__ 运算符重载从 Python 2 就有（int | int 是位或、set | set 是并集）， LangChain 只是借用了这个一直存在的机制；Python 3.10 新增的是类型标注里的 X | Y （str | None 那种，PEP 604），两者是两回事。

这正是你项目里记过的那类风险：教程会写错，而且写错的地方往往听起来很顺。 所以这个知识点以你本机跑出来的输出为准，文章只当辅助。

4动手 · 写 lcel_demo.py

新建 week1-basics/day05-lcel/lcel_demo.py，骨架可直接粘。 模型初始化那段和你 D1 的 hello_model.py 完全一致（同样读仓库根的 .env）。

"""D5 · LCEL 管道（最小可运行）

今天验证三件事：
① 管道符 | 到底做了什么 —— 上一个 Runnable 的输出 = 下一个的输入
② 同一条 chain，四种调用方式都成立：invoke / stream / batch / ainvoke
③ 形状对不上时怎么排查 —— 先看「第一个环节要什么输入」
"""
from __future__ import annotations

import asyncio
import os
import time
from pathlib import Path

from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate

REPO_ROOT = Path(__file__).resolve().parents[2]
load_dotenv(REPO_ROOT / ".env")

MODEL = os.getenv("DEEPSEEK_MODEL", "deepseek-chat")
BASE_URL = os.getenv("DEEPSEEK_BASE_URL", "https://api.deepseek.com/v1")
API_KEY = os.getenv("DEEPSEEK_API_KEY")


def build_chain():
    """把三个 Runnable 串成一条链。今天要理解的就是这一行。"""
    if not API_KEY:
        raise SystemExit("没读到 DEEPSEEK_API_KEY，先检查仓库根的 .env。")

    prompt = ChatPromptTemplate.from_messages([
        ("system", "你是一个说话极简的中文助手，回答不超过 30 个字。"),
        ("user", "{question}"),          # <- 这个占位符，决定了 invoke 要传字典
    ])
    model = init_chat_model(
        MODEL,
        model_provider="openai",
        base_url=BASE_URL,
        api_key=API_KEY,
        temperature=0,
    )
    return prompt | model | StrOutputParser()


def main() -> None:
    chain = build_chain()

    # ① invoke —— 同步，一次一个问题
    print("① invoke：", chain.invoke({"question": "用一句话解释什么是管道符"}))

    # ② stream —— 逐块拿，打字机效果的来源
    print("② stream：", end="", flush=True)     # flush 必须有，否则看不到逐字效果
    for chunk in chain.stream({"question": "写一句关于管道符的顺口溜"}):
        print(chunk, end="", flush=True)
    print()

    # ③ batch —— 一次给多个输入，内部并发
    answers = chain.batch([
        {"question": "1 的三次方是多少"},
        {"question": "2 的三次方是多少"},
        {"question": "3 的三次方是多少"},
    ])
    print("③ batch：", answers)

    # ④ ainvoke —— 异步版本，顶层不能 await，用 asyncio.run 包
    print("④ ainvoke：", asyncio.run(chain.ainvoke({"question": "用一句话介绍你自己"})))

    # ⑤ 附赠：batch 和 for 循环的耗时对比（今天的实验数据）
    questions = [{"question": f"{n} 的三次方是多少"} for n in range(1, 6)]

    t0 = time.perf_counter()
    for q in questions:
        chain.invoke(q)
    t_for = time.perf_counter() - t0

    t0 = time.perf_counter()
    chain.batch(questions)
    t_batch = time.perf_counter() - t0

    print(f"⑤ 5 个问题：for+invoke {t_for:.2f}s ／ batch {t_batch:.2f}s")


if __name__ == "__main__":
    main()

三处要你自己动脑子改的地方

  1. 把 | StrOutputParser() 去掉再跑一遍，看 print 出来是什么。 你会拿到一个 AIMessage 对象而不是文字 —— 这是理解「管道两端形状要匹配」的最快方式。
  2. 故意传错输入：写一次 chain.invoke("你好")（字符串，不是字典），记下报错长什么样。 以后看到类似报错，就知道是第一个环节在要变量。
  3. 给 for + invoke 和 batch 各记一个数，不要预设结论。 谁快谁慢取决于网络和并发限制，你测出来的数才是数据。

做法：写 pipe_proof.py 先用零 token 的方式确认语义 —— type(a | b) 是 RunnableSequence，

      prompt.invoke() 吐 ChatPromptValue，下游探针收到的也是 ChatPromptValue，是同一个对象；
      再接回 StrOutputParser，输出恢复成字符串
结论：管道符就是「上一个的输出成为下一个的输入」；invoke 传什么由链的入口决定
      —— 入口是 ChatPromptTemplate，所以要传变量字典，不是字符串

7坑预警

症状真实原因
以为 chain.invoke("你好") 会报错 不会 —— 这是个陷阱。模板只有 1 个变量时，非 dict 输入会被自动塞进那个变量 （源码 langchain_core/prompts/base.py:163，「单变量特例」）。 但只要模板加到 2 个变量，同样写法立刻 TypeError。 → 所以永远显式写 chain.invoke({"question": "你好"})，别依赖这个便利
⚠️ 别和 model.invoke("你好") 混了 —— 那个也是合法的，但走的是另一条机制： ChatModel._convert_input()，其中 str / 消息列表 / PromptValue 是它定义内的合法输入，与变量数无关、永远成立（D4 里一直这么用，没问题）。
口诀：model 收 str 是「契约」，prompt 收 str 是「宽容」
print 出来是 AIMessage(content=...) 一大坨 忘了接 | StrOutputParser()。这不是报错，是类型没转换 —— 正好当实验
stream 看不出逐字效果 ① 忘了 flush=True（PyCharm 控制台会缓冲）； ② 写成了 print(chunk) 而不是 print(chunk, end="", flush=True)
把类型注解的 | 和管道符搞混 str | None 是 Python 3.10+ 的联合类型；LCEL 的 | 是 Runnable.__or__。 两者毫无关系，但这是个好面试谈资
await chain.ainvoke(...) 报 SyntaxError 顶层不能 await，要用 asyncio.run(...) 包起来
init_chat_model 导入报错 确认是 from langchain.chat_models import init_chat_model（1.x 的路径）， 不是老教程里的 ChatOpenAI
想去翻老教程找 LCEL 章节，越看越乱 搜到的基本是 v0.2 时代的 LLMChain / SequentialChain。 看到这些词直接关掉
