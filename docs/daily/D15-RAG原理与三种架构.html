再读 RAG architectures 那张表（10 分钟，重点）

这就是计划表说的「三种架构」，原文只有一张四列表，我把它抄在这里（内容来自官方页面，未做改写）：

架构一句话控制力灵活性延迟
2-Step RAG 检索永远在生成之前，一条直线 高低快
Agentic RAG 由 agent 在推理中自己决定什么时候、怎么检索 低高不定
Hybrid 两者混合，中间加校验步骤 中中不定

读这张表只问自己一句：为什么 Agentic 的「灵活性高」反而意味着「控制力低」？

因为控制权转移了。2-Step 里你知道它一定会检索、一定检索 top-k、一定拼进 prompt——每一步都可预测，出了问题能定位。 Agentic 把「要不要检索」交给模型判断，模型可能不查就答，也可能查五次。能力上限更高，但你不再能保证它做了什么。

最后读三小节各一段（13 分钟）

小节读什么为什么读
2-step RAG 只有一段话，说明检索是生成的前置条件 D19 你要写的第一个 MVP 就是这个架构
Agentic RAG 看代码示例：一个 @tool 包住检索，就完成了 RAG 你 D9–D14 写的全是这个模式，只是工具换成了「查资料」
Hybrid RAG 三个组件的名字：query enhancement / retrieval validation / answer validation D20「检索优化」就是在这三个位置各加一道工序

读到这里你会发现：这三种架构你这周已经手写过了。

2-Step = 你在 D10 写的「先查询、再回答」；Agentic = 你在 D9 写的手写循环，模型自己决定调不调工具； Hybrid = 你在 D11 试过的「工具报错后重试」。RAG 没有新机制，它只是把「工具」换成了「检索器」。

这也是为什么 D15 不给代码 —— 机制你已经会了，今天缺的是一套自己的数据。

硬性条件（四条，缺一条就换）

  1. 规模 20–500 个文件。少于 20 个，检索永远是「全命中」，测不出召回率；多于 500 个，D19 建索引要等太久。
  2. 你读过其中至少三分之一。否则检索结果对不对，你自己判断不了——这是最容易翻车的地方。
  3. 能回答 3 个具体问题。问题必须在这套语料里有明确答案，且答案有唯一出处。
  4. 可以公开。公司内部资料、含个人信息的文档，一律不放。

写 3 个具体问题（今天最值钱的产出）

每条按这个格式写，四行，缺一行都不算完成：

问题 1：影石 X4 的最大防水深度是多少（裸机 / 带壳）？
现在怎么查：官网 → 产品页 → 规格表 → Ctrl+F 搜「防水」，3 步，约 40 秒
慢在哪：规格表是图片，Ctrl+F 搜不到，只能肉眼找
为什么值得做：这类参数客服每天被问几十次，答案固定但查找成本高

「慢在哪」这一行是 D34 提效度量的基准线。现在写不出具体数字（几步、几秒），三周后就没有对比对象， 最后只能写「感觉快了一点」——那种结论在面试里一文不值。
