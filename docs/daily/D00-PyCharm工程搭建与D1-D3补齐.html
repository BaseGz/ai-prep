1为什么必须另开一个工程

  1. 旧文件夹不是 git 仓库。（我确认过：里面没有 .git）在它里面学的产出进不了版本库，面试官点开你 GitHub 什么都看不到 —— 那你 35 天白做。
  2. 旧工程解释器是 conda base。在里面 pip install 会把包装进 miniconda 全局，以后任何项目都被牵连；而且它是 3.14.7。
  3. 版本会打架。旧工程 pin 的是 langchain==1.2.12，新仓库要 1.4.2。同一个解释器里两边装着，一定互相覆盖，报错还很难查。
  4. Ctrl+K 只看一个仓库。PyCharm 工程根 = 仓库根，提交列表里就只出现这一个仓库的改动。两个仓库混在一个工程里，你每次提交都得手动取消勾选，早晚会误提交。

为什么必须留在 Windows 方案：设置 → 按键映射 → 右上角下拉有 Windows / Emacs / Sublime Text / VSCode 四套。你截图上选的是 Windows，保持它别动。 一旦切成 VSCode 方案，Ctrl+K 会变成「和弦键前缀」（要先按 Ctrl+K 再按别的键）， 我们后面 35 天所有 Ctrl+K 提交、Alt+9 打 tag 的指引会全部失效 —— 这不是坏了，是方案换了。

那四套里 Alt+Enter 导包只属于 Windows 方案；Emacs / Sublime / VSCode 方案下这个组合键不是导包。 想确认某个动作在你的方案下绑了什么键：在「按键映射」页 搜索框里搜动作名（中文界面搜中文名，搜不到就搜英文）， 再按 位置看它落在哪一组。

按了 Alt+Enter 却没看到「导入」项？导包那一项的中文名是 「导入此名称」（英文 Import this name），通常排在列表第一行。三种情况下它不会出现：

  1. 这个类已经导入过了 —— 最常见。看文件顶部有没有 from langchain_core.messages import ...； 类名没有红色波浪线（紫色 = 已解析）就说明已经导好了，没有东西需要导。
  2. 当前有文字被选中 —— 这时列表给的是「选区意图」（如「从选区创建新的临时文件」「将 list 转换为 set」「注入语言或引用」）， 导入项会被挤掉。先按 Esc 或点一下别处取消选区，把光标单独放进那个类名里再按。
  3. 解释器没配好 / 包没装 —— 类名不报红也不报「未解析」，因为 IDE 根本没在检查。

另：notebook（.ipynb）单元格里 Alt+Enter 的导入修复不如 .py 文件可靠， 同一个类名前一个单元格导过、后一个单元格能用，是正常的（所有单元格共用一个内核）。

中文包的一个坑：翻译并不覆盖所有字符串，有些版本更新后新加的界面元素仍是英文（比如对话框标题可能还是 Add Python Interpreter）。所以以上按位置找，别只认文字 —— 四个输入项的顺序永远是 位置 → 基础解释器 → 两个勾选框。

为什么不要直接搬 .ipynb

  1. 新仓库没装 jupyter。依赖清单只有 langchain 三件套，notebook 打不开也跑不了。

  3. 面试官要读的是 .py。notebook 的 JSON 里混着图像输出，diff 一行都读不出来。.py 才是一眼能看懂的。
所以"挑选"的正确姿势是：打开旧 notebook 当参考 → 在新仓库里重写成 .py → 跑通。 重写一遍不到 20 分钟，但产出是"我写的代码"，不是"我抄的文件"。 D1–D3 都是轻内容（环境 / 换模型 / 流式），一天半足够全补完，09-23 还能留半天机动。
