Git 提交规范与分支约定

一、为什么需要规范

提交信息是代码仓库里唯一无法被重构的东西。代码可以随时重写，分支可以随时合并，但三个月前那条写着"修了一下"的提交记录会永远留在历史里。当你在排查一个线上问题时，需要在几十条提交中找到引入缺陷的那一次，提交信息的质量直接决定你要花五分钟还是五十分钟。

这一份约定不是为了让日志好看，而是为了让日志可用。它的目标是：任何人只看提交记录，就能还原出这个仓库发生过什么、为什么这么改。

二、提交信息的结构

一次提交由标题和正文两部分组成，中间空一行。标题一行封顶，正文按需要分段。

标题的格式是"类型: 简短描述"，类型从下面四个里选一个：

- feat：新增功能
- fix：修复缺陷
- refactor：不改变外部行为的结构调整
- docs：只动文档

描述部分用祈使句，说明这次改动做了什么，不写"我"、不写"已经"、不用句号结尾。控制在五十个字符以内，超过说明这次提交包含的事情太多，应该拆开。

正文回答三个问题：为什么要改、改之前是什么状态、改之后是什么状态。不写"怎么改的"，那是 diff 的事，代码本身已经说清楚了。

三、一个完整的例子

假设你在处理一个分页接口的缺陷，用户反馈第 12 页之后全部返回空列表。你排查后发现排序字段在分页查询里用了非唯一列，当多行记录的排序值相同时，数据库返回的顺序不稳定，导致相邻两页之间出现重复和遗漏。修复方式是在排序条件里追加主键作为次级排序键，保证顺序全序化。这是一个典型的"症状在表层、根因在查询层"的问题，如果只写"修复分页 bug"，半年之后有人再碰到类似现象时，无法从提交记录里得到任何线索。合格的写法在正文里交代清楚现象、最初的判断偏差、实际定位到的原因，以及这次改动为什么能消除这个原因而不是掩盖它。这样的正文通常三到五句话，不超过两百字，写的时候要把自己当作半年后的陌生人，假设对方完全不知道今天发生了什么，只能读到这段文字。判断标准很简单：如果半年后的你读到这段正文，能不能在五分钟内决定"要不要回滚这次提交"，如果能，它就合格了；如果读完仍然要去翻 diff 才知道改了什么，那么这段正文等于没写。另外要注意，正文里的每一句话都应该提供新信息，删掉任何一句都不会让读者少知道什么，那就应该删掉。

四、分支命名

分支名用"类型/简短说明"的格式，类型和提交标题的前缀保持一致。例如 feature/pagination-fix、docs/api-reference。

分支名全部用小写，单词之间用连字符，不要用下划线或驼峰。中文操作系统的文件系统对大小写不敏感，但远端仓库是大小写敏感的，混用会在某些路径上产生难以复现的问题。

分支的生命周期尽量短。一个分支从创建到合并控制在三天以内，超过一周的分支基本会积累到无法顺利合并的程度，那时处理冲突的成本远高于重新做一遍。

五、合并与推送

合并前先把主干的最新改动拉到本地并解决冲突，再执行合并。这样做的原因是冲突在本地解决成本最低，一旦推到远端再发现冲突，就需要额外一轮提交来收拾，历史会变得难以阅读。

推送之前检查三件事：本地是否还有未提交的改动、分支是否落后于远端、提交信息是否还有占位内容。第三条最容易被忽略，模板里的"描述你的改动"直接提交上去的情况并不罕见。

六、常见错误

- 一条提交里混了格式化和功能改动
- 标题写了"更新"，正文空白
- 提交前没有跑测试
- 把调试用的 print 一起提交
- 分支名用中文
- 提交信息写成了日报
- 一个功能拆成十几条"补充"提交
- 合并时用了默认的 merge message
